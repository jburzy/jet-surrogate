Contribute an analysis

Analyses are added to our library by pull request. Bring the record, the surrogate model files, a model card and your validation figures.

Before you start

A contribution is a surrogate for one preserved analysis: a model that takes generator-level events and predicts whether the analysis would select them. The inference code ships with the analysis as predictor.py (see below), so the service needs no change for a new model type. If your predictor needs a Python package the runner does not have, add it to the infer environment in the same pull request.

Please make sure the model files and validation figures are approved for public release by your collaboration before opening the pull request.

Steps

  1. Fork the repository and create a directory analyses/<analysis-id>/. The id is lowercase with hyphens and becomes the URL of the analysis page.
  2. Add analysis.yaml following the schema below. The signal_region text is shown next to every result, so describe the selection precisely.
  3. Add the surrogate model files named in the record.
  4. Write README.md, the model card: what the analysis selects, which samples the surrogate was trained on, how it was validated and where it should not be trusted.
  5. Put validation figures in figures/ (PNG) and list them in the record with captions. Optional validation rows become a table on the analysis page.
  6. Open a pull request. Our CI validates the record and checks that the model loads. A maintainer reviews the model card and validation and merges. The analysis appears in the library on the next deployment.

Directory layout

analyses/
  my-analysis-id/
    analysis.yaml        # the record (schema below)
    README.md            # model card: what the analysis selects, how the surrogate was trained and validated, known limits
    surrogate.pt         # model file(s) named in the record
    figures/
      sr_efficiency_m5.png
      closure_probability.png

Record schema

analysis.yaml

id: my-analysis-id            # directory name, lowercase, hyphens
title: Search for ...
short: one-line description
experiment: ATLAS | CMS | LHCb | other
status: example | preserved
version: "1.0"
updated: 2026-08-29
contact: name <email>
references:
  - {label: "arXiv:2505.02429", url: "https://arxiv.org/abs/2505.02429"}
signal_region: text describing the selection the efficiency refers to
inputs:
  - HepMC2 or HepMC3 ASCII, generator level, ...
predictor:
  type: jet_surrogate            # a registered predictor type
  model: surrogate.pt
default_max_events: 20000
max_events: 50000
validation:                      # optional table rows shown on the analysis page
  - {sample: "...", actual: 0.43, predicted: 0.38}
figures:                         # optional, files in figures/
  - {file: sr_efficiency_m5.png, caption: "..."}

default_max_events pre-fills the submission form and max_events caps what a single job may process. Choose them so a job finishes in minutes on our worker. Bump version and updated whenever the model or the record changes, since both are shown with every result.

Questions

Open an issue on GitHub or contact the maintainers listed in the repository. We are happy to help wire up a new predictor type.

Bringing your own predictor

Most surrogates need their own inference code: which objects to take from the event record, which features to build, which model library to call. That code lives with the analysis, as predictor.py next to analysis.yaml, so the main package stays small and each analysis is self-contained. The file defines one class, a Predictor subclass decorated with @register("<type>"), and analysis.yaml names that type in predictor.type. The two library entries are worked examples: a truth-jet transformer with a Poisson-binomial event probability (emerging-jets-delphes) and published scikit-learn forests on displaced-vertex features (atlas-exot-2022-04-calratio). 

from jet_surrogate.service.predictors import Predictor, finish_summary, register

@register("my_bdt")
class MyBDT(Predictor):
    def __init__(self, analysis, device="cpu"):
        super().__init__(analysis, device)
        import xgboost
        self.booster = xgboost.Booster(); self.booster.load_model(str(analysis.model_path))
        self.config = analysis.record["predictor"].get("config", {})

    def run(self, hepmc, max_events, progress=None):
        from jet_surrogate.hepmc_io import read_hepmc
        probs = []
        for batch in read_hepmc(hepmc, max_events=max_events):
            x = event_features(batch.part, self.config)      # any function of the event record
            probs.append(self.booster.inplace_predict(x))
        per_event = np.clip(np.concatenate(probs), 0, 1)
        yield_ = [{"name": "expected signal-region yield", "value": float(per_event.mean() * sigma_pb * 1e3 * lumi_fb),
                   "unit": "events", "note": "for 1 pb and 140 fb^-1"}]
        return finish_summary(self.analysis, {}, per_event, quantities=yield_), per_event, {}

read_hepmc yields batches with every particle of every event (identity, status, mother and daughter links, kinematics, production vertices), so the class selects whatever objects and features the model needs. finish_summary fills the fields every result carries (efficiency and its uncertainty from the per-event probabilities, the histogram, provenance); objects and quantities add whatever else the analysis wants shown, for example the yield in region A of an ABCD plane for a stated cross section. List the Python modules the predictor imports under requirements in analysis.yaml (CI checks them) and add them to the infer feature of pixi.toml in the same pull request. The analyses/_template/ directory is a complete starting point, and tests/test_predictor_plugin.py shows a whole toy analysis running through the service.

Two more record keys cover common needs. assets lists large model files that should not live in git ({name, url, extract}, for example Zenodo tarballs): they are downloaded once into the service's asset directory and reached from the predictor as analysis.assets_dir / name. options declares per-job choices ({name, label, choices, default, help}), shown as a selector on the submit page and passed to run(..., options=...), for example which of several selections of a paper to evaluate. The ATLAS CalRatio entry (analyses/atlas-exot-2022-04-calratio/) uses both: its six published scikit-learn BDTs are fetched from Zenodo and the selection is a job option.
